# CleanFlow

A personalized planner for your home and everyday life: cleaning, movement, meals and shopping, learning and hobbies, wellbeing. You describe your home, time and energy; a rule-based
engine builds a realistic plan, with tiny-step and "just 5 minutes" modes for overwhelmed days.

## Run it

```bash
npm install
npm run dev        # http://localhost:5173
npm test           # 653 tests at the time of writing: engine, scheduler, daily budget, low-energy safety, goal coverage, persistence, backups, retention, reducer, analytics
npm run build      # typecheck + production build into dist/
npm run check      # type-check + tests
npm run e2e        # eleven browser suites: flow, responsive (7 widths), integrity, sync (two tabs), behaviour (what a day records), coach (Your patterns and the optional AI), sections (sections and the shared plan), meals (meals, recipes and shopping), movement (movement, water and wellbeing), learning (learning, hobbies, reading, appearance and the owl), assist (the assistant, reminders and health settings). The dev server must be running; set CHROME_PATH if needed
npm run dev:coach   # dev server with ANTHROPIC_API_KEY read from the macOS Keychain (see "Try it on your Mac")
npm run sample-data # writes made-up history for trying Your patterns and the coach
npm run build:server && npm start   # optional: one Node process serving the built app and the AI coach endpoint (see "AI coach")
```

By default there is no account: your plan and history live in `localStorage` and the app needs no server. The optional AI coach endpoint (see "AI coach") is the only server code the single-device app uses, and without it everything else works exactly the same. A server can also run the app in **accounts mode** (sign-in, a free trial, a subscription, an optional cloud backup): see "Accounts, the free trial and subscriptions" below, which says what is verified and what is not. The Welcome screen (and Settings) can load seven example profiles.

## Architecture

```

  context.ts      Home + Preferences → rooms, zones, floors, planning context (visibility rules per home type)
  catalog.ts      130 home task templates (rules, not tasks): scope, scaling, frequency step-ups, steps, tiny steps, reasons
  engine.ts       instantiate → scale → step frequencies → split → fit to weekly capacity → explain (PlanNote[])
  planner.ts      scheduler: reset phase first, habits, weekday-balanced slotting grouped by zone/room
  schedule.ts     recurrence, overdue rolling, complete/skip/snooze/move transitions, overrides
  budget.ts       the one daily time budget and the single fit that decides what a day holds (Today, Tomorrow, Schedule)
  safety.ts       the one low-energy rule every list that suggests a task must use
  retention.ts    how much history fits in browser storage, and how it is thinned and then trimmed (never silently; thinning.ts holds the pieces)
  modules/        sections (movement, meals, learning, wellbeing, water) and the planned activities that put them in the one plan
  meals/ movement/ water/ wellbeing/ interests/   each section's content and pure logic (catalogues, planners, guided session, shopping arithmetic, discover)
  appearance/ owl/   palettes with contrast checks, applying a look to the page; the owl's rule-based tips
  assist/         the assistant: request and proposal contracts, candidates built on the device, the app's own suggestion, approval into actions
  reminders/ health/   reminders derived from the plan (planner, calendar file, platforms, sync); read-only health data (adapter, status, merge)
  view.ts modes.ts micro.ts learning.ts progress.ts supplies.ts timer.ts   selectors and features
src/storage     Repository interface + LocalStorage adapter (swap for a real DB here)
src/state       reducer (pure, one small reducer per section), store (React context, timer, toasts, undo), chime, the appearance and reminder runtimes
server/         the optional AI: coach/ (counts explained) and assist/ (candidates chosen), mounted together by api.ts
src/features    onboarding, today, plan, schedule, progress, home, supplies, modes, tasks, settings, sections, activities, meals, movement, wellbeing, learning, assist, health
```

### Life layer (discipline & lifestyle)
Beyond cleaning, CleanFlow can build small daily habits across nine areas: fitness, breathing, personal care, mind & focus,
digital discipline, life admin, learning, outdoors and sleep. It is opt-in: onboarding starts with **"What do you want to improve?"**
(`Preferences.focus`); home questions are skipped if you don't want a cleaning plan, and older saved data defaults to home-only.

```
src/domain/lifeCatalog.ts   86 templates, each with a progression ladder (walk 5→10→20→30 min) instead of near-duplicates, plus redundancy groups so near-duplicates never share a plan
src/domain/goals.ts         an explicit rule, in words, for every goal: what counts as primary cover, how long a step must be, and why
src/domain/progression.ts   when someone is ready for more (or less): distinct days over a minimum period at the current level
src/domain/life.ts          selection: focus → ladder step → daily time budget → per-weekday load check; challenges; rough-day reset
src/domain/scoring.ts       shared frequency ladder / priority / isLife()
```
- **Manageable:** ONE daily time budget, the number the user chose. Cleaning and habits share it 60/40 when both are on (each gets all of it when alone), and unused minutes in one share go to the other. `fitDay` decides every day, for Today, Tomorrow and the whole schedule alike, so what is planned never adds up to more than the promise. The only exception is an urgent task the user added themselves: it is kept, the overage is shown as an exact number, and everything else is left out. Anything that does not fit is listed as *left out*, with the reason (time, low energy, or not a cleaning day), and stays due; a task that has waited two days moves ahead of newer work. A habit cap (3–8) keeps the list short.
- **Honest about goals:** a goal counts as covered only when a chosen task is *primary* for it: it passes the goal's own rule (for example, "Moves your body for 5 minutes or more") and the step is long enough. Related tasks are shown as *supporting*, with the reason they are not enough on their own. The Plan page names each goal's task, its minutes, whether it is primary or supporting, and why it counts. Goals that do not fit are *deferred*, and the reason is where the goal actually stopped being possible: not enough minutes (with the number needed), the habit cap, a safety limit, something missing (such as equipment), or no suitable task at the current level.
- **Time-aware:** Today splits habits and home routines into Now (this part of the day plus anytime tasks), Later today, This evening and Earlier today, so an evening routine is never presented as a morning task. Cleaning is not clock-driven: only the few tasks that belong to a time of day (making the bed, the evening dishes) are tucked away, never hidden.
- **Progressive:** `lifeLevel` 1–3. The next ladder step is an optional *challenge*, never scheduled. A step up is suggested only after three weeks at a level with habits done on 15+ distinct days across the week; easing off needs 10+ days and real evidence. Fitness starts at the user's fitness level (beginner / intermediate / advanced), moved by their chosen pace. Nothing changes without a yes.
- **Safe:** fitness is filtered by fitness level and equipment (bodyweight by default), volumes are modest, and fitness/breathing tasks always end with a safety line. No medical claims. On a day the user marks as low energy, hard and vigorous tasks are held back by *every* list that suggests something (Today, Quick wins, "I only have X minutes", Just 5 minutes, challenges, routines, room lists, the reset sequence), all through the same `energyOk` rule, and the day's minutes shrink to 60%. With very low energy no habit runs longer than 15 minutes.
- **Separate from cleaning:** room mode, deep clean, reset sequence and supplies only use home tasks; life habits run every day, including non-cleaning days. People who do not choose a cleaning plan get no home screens at all ("My goals" instead of "My Home", no supplies, no home reset).
- **Rough-day reset** ("Back on track"): up to four tiny, gentle actions, never more than ~12 minutes.

### How personalization works
1. **Context** – size class, rooms (per floor), people/kids tier, pets, mess level, energy, blockers, goals, active days, chunk size.
2. **Instantiate** – each template applies per room/floor/home only if the home has that space (dorm ≠ garage).
3. **Scale & step** – minutes scale with room area and household size; frequency steps up for people, kids, shedding pets.
4. **Split** – tasks longer than the session/energy limit become "part 1 of N".
5. **Fit** – weekly load is fitted to `session × days`: relax low-value tasks (max 1–2 levels), park the rest in a backlog. Essentials never relax.
6. **Schedule** – reset tasks first (maintenance deferred for messy homes), daily habits run even on rest days, the rest is balanced by weekday and grouped by zone.
7. **Explain** – every adaptation is recorded and shown ("Why this plan?").

Learning is rule-based and always asks first (shorter sessions, repeated skips, steady routines, a step up or an easier stretch). What each rule reads, and what it refuses to read, is under **Behaviour insights** below.

## Sections and the one shared plan

CleanFlow plans a whole day, not only cleaning. A person switches on only what they want (Settings → *What you use CleanFlow for*): **Home & cleaning**, **Movement**, **Meals & shopping**, **Learning & hobbies**, **Wellbeing** (and, when it ships, **Water**). Nothing is pre-selected for a new person, and a person who had the app before sections existed is never asked to onboard again: `src/storage/schema.ts` migrates v2 → v3, turns a section on only where a goal they already chose points at it (Active/Healthy → Movement, Study → Learning, Self-care/Morning/Evening → Wellbeing), and shows a one-time introduction.

- **One planner.** Anything planned in a section is a `PlannedActivity` (`src/domain/modules/`) and becomes an ordinary `Task` with the id `act:<activityId>`, so Today, the Schedule, the timer and the log treat it like cleaning. An activity has one identity and one completion record, whichever section shows it.
- **Three kinds.** *Fixed* (a clock time the planner never moves; overlapping fixed times are reported as a conflict), *flexible* (counts against the day), *optional* (an idea: never counted, never due). Tracking-only things (meals eaten, water, mood) are not tasks and never use the day's minutes.
- **What the daily time covers.** One number covers everything a person plans for a day: cleaning, habits, workouts, hobbies, learning and meal prep. Not eating, sleeping or drinking water. Something the person planned is never dropped for time: if it is longer than the day, Today says by how many minutes, and nothing is moved without asking. The low-energy safety rule still applies to a planned vigorous workout. An optional per-section daily allowance holds back what the planner suggests; what the person planned stays and is flagged.
- **Scheduled, completed, skipped, not recorded.** A scheduled day with nothing logged is *not recorded*; it is never read as skipped, failed or zero (`activityHistory`).
- Turning a section off hides it and keeps everything in it.

## Meals, recipes and shopping

Switch on **Meals & shopping** and the person gets a weekly planner, a recipe catalogue, shopping lists made from the plan, and a Meals card on Today. Code: `src/domain/meals/`, UI: `src/features/meals/`.

- **What a meal can be.** A starter recipe, a dish the person wrote down (real ingredients and amounts), a free-text log with no recipe, or leftovers from an earlier batch (which add nothing to shopping). Breakfast, lunch, dinner and snack are each optional, with an optional time the person chose.
- **Planned, prepared, eaten, skipped, not recorded.** Only an explicit answer makes a meal eaten or skipped. A past meal nobody recorded is *not recorded* (`mealState`), never skipped. A meal is *prepared* when it is marked so, or when its linked cooking session (a planned activity) is completed: one record, so undo works.
- **23 starter recipes** (`recipes.ts`) are written for this app, use everyday ingredients, and are mostly meat-free. They have structured ingredients, quantities, units, servings, prep and cook times and original method text. **They carry no nutrition figures and no prices**: the app has no verified source for either, and a test enforces it. A person may type their own calorie number on a dish or meal; it is never computed, and nothing sets a calorie target, weight goal, fasting window or medical diet.
- **Diet and allergens** are filters on the ingredients a recipe lists, using one ingredient catalogue (`ingredients.ts`). Flags are deliberately cautious and are not a guarantee; the app says so wherever it shows them. A recipe with ingredients the catalogue does not know is left out of suggestions whenever a diet or allergen filter is on, because it cannot be checked.
- **Shopping arithmetic is plain code** (`shopping.ts`, `units.ts`). A recipe is scaled to the servings planned; every ingredient has one identity ("tomatoes" and "tomato" are one line); amounts are added only inside a family (mass: g/kg; volume: ml/l/tsp/tbsp/cup, with fixed cooking definitions); amounts that need a density to convert (grams against pieces) stay as separate lines; optional ingredients are their own lines; counted things are rounded up to whole ones once, on the total, while each meal's exact share stays under "needed for". Every line names the meals that need it.
- **When the plan changes,** a list does not change by itself. `proposeUpdate` computes what would change; the person reviews it and applies or ignores it. Items they added, what they ticked off, what they marked as at home and any amount they edited are kept; a line they already bought is never silently removed. An ignored proposal stays quiet until the plan changes again.
- **Sharing.** A list exports as plain text grouped by aisle (share sheet where the browser has one, otherwise copy, otherwise a download).

## Movement, water and wellbeing

- **Movement** (`src/domain/movement/`, `src/features/movement/`): 37 exercises and 14 starter workouts in six kinds (walking, mobility, gentle, strength, stretching, dance), each exercise with clear steps and an easier version, filterable by kind, level, time, impact, and the equipment and "would rather not do" choices the person gave. Workouts of one's own can be built from the catalogue or from named exercises; their minutes are worked out from sets, reps or time, and rests. **Minutes are counted once:** a whole workout is one log entry with its real duration; the exercise records carry no minutes at all (a test pins their exact keys). A guided session (start, pause, rest, next, skip, easier, end) is a pure state machine (`session.ts`) that counts only running time, catches up from the wall clock, and survives a reload. A session can be logged against a planned workout instead of on its own, and is still one entry.
- **No escalation, no pressure.** Nothing sets a weight, calorie or body goal. Difficulty never rises by itself: after three easy sessions of a workout the person may be *offered* a step up; after "hard" twice, or after stopping because of pain or discomfort, only the easier version is offered, and the message says nothing is pushed. The low-energy rule still applies to anything planned, and on a low-energy day only gentle workouts are suggested. A workout planned on a declared rest day is flagged, never moved. A week with nothing logged says "nothing logged yet", not zero. All instructions are general guidance, not medical advice; tests forbid medical, weight and "push through" wording.
- **Water** (`src/domain/water/`): a log of amounts and times, with quick amounts, custom amounts (impossible numbers refused, surprising ones confirmed), editing, Undo, units (ml, fl oz, cups), and an *optional goal of the person's own*. The app suggests no target: needs differ and it cannot know them. A day with nothing logged is unknown, not zero; the history averages only logged days; reaching one's own goal says only that, never more.
- **Wellbeing** (`src/domain/wellbeing/`): self-reported check-ins (energy and mood, optional note), a private journal, a breathing guide, and starter routines. Energy in a check-in is the same answer Today's list already uses, and the screen says so before saving. Nothing is scored, interpreted or diagnosed; breathing and routines make no treatment or sleep claims (tested). Journal text and check-in notes stay on the device.

## Learning, hobbies, appearance and the owl

- **Learning and hobbies** (`src/domain/interests/`, `src/features/learning/`): a short built-in list of 17 starting points (reading, singing, an instrument, rhythm, dance, drawing, painting, sewing, paper folding, a language, writing, noticing nature, phone photography and more), each with small first tries (steps, minutes, what you need), plus interests you make up yourself. **The app names no book, author, course, channel or link:** anything of that kind is typed by the person (a link is stored only if it is a plain http or https address). *Discover* is a plain filter on time, budget, indoors/outdoors and company, with the reason for every suggestion; "Enjoyed it" in a category lifts that category a little, "Not for me" removes an idea, and the screen says that is a simple rule and not a guess about the person. A first try adds nothing to the list until it is tried. Sessions are logged once (one log entry holds the minutes; the session record holds what it was, how it felt and what was used), either on their own or against something planned. A reading list (want, reading, finished) has optional page counts. Nothing here is due, scored or a streak; "nothing logged lately" is not a miss.
- **Appearance** (`src/domain/appearance/`, `src/features/settings/AppearancePanel.tsx`): light, dark or follow the device; five coordinated palettes; an optional accent of the person's own, **always adjusted until text on it is readable (and the screen says when it adjusted it)**; four system-font styles (nothing is downloaded: the page makes no font request); four text sizes that scale the whole interface; comfortable or compact spacing; and reduced motion, either chosen here or following the device. Every palette in light and dark, and any accent, is held to WCAG contrast minimums for every text pair by tests. The choice is saved with the data (so it is in backups) and mirrored in a small device copy that a few lines in `index.html` apply before the first paint, so there is no flash of the wrong theme. An older light/dark setting carries over once. Dark now works whatever the device is set to (an earlier version only honoured "light" on a dark device).
- **The owl** (`src/ui/Owl.tsx`, `src/domain/owl/tips.ts`): original artwork drawn from a few shapes in the page's own colours, with calm idle, thinking, success and asleep states. It stands still with reduced motion, is never placed over a control, and can be hidden at any time. Its tips come from fixed, visible rules (for example "you have meals planned and no shopping list") and are labelled **"App tip, not from the AI"**; a dismissed tip stays dismissed; none uses pressure, streaks or health claims (tested). It works without any AI key.

## Safety
The Supplies screen shows a permanent chemical-safety warning (never mix products, especially bleach with ammonia or acids) and warns when the user's own stash contains dangerous pairs. The app never gives mixing instructions.

## Data safety
- **Saved data is never silently destroyed.** `src/storage/schema.ts` validates and repairs on load (bad fields are repaired, bad list items dropped and counted) and migrates by version (`SCHEMA_VERSION = 3`). A file from a newer version is read as far as possible and backed up. Data that cannot be understood is kept as raw text and shown on a **recovery screen** (download it, restore an automatic backup, or start fresh, which keeps a copy first).
- **An error boundary** wraps the app (full recovery screen) and every page (the navigation keeps working).
- **Anything that replaces your data asks first** (demo, restore from file or backup, erase) and takes an **automatic backup** (last three, listed in Settings). Erase offers a download first and deletes the backups too.
- **Exports are versioned envelopes** (`{ app, exportVersion, schemaVersion, data }`); imports also accept the bare files older versions wrote, and show a summary before replacing anything.
- **Saves are revision-checked.** Two tabs cannot overwrite each other: the stale tab takes the newer data and replays its own unsaved actions on top. Only a real local change ever writes a new revision: adopting another tab's save does not, so two open tabs settle and then go quiet (the browser suite counts the writes). Saves flush on `pagehide` and bring the tab up to date with whatever it merged. A full disk or blocked storage shows a banner instead of failing silently.
- **A safety copy is verified before anything is replaced.** Replacing your data first brings in anything another tab saved, then copies and checks the copy. If there is no room for the copy, nothing is replaced until you have downloaded your own. Identical backups are kept once, and one of each kind is kept in preference to three of the same.
- **History is never dropped silently.** Storage holds about 5 million characters. `scripts/storage-growth.ts` measures real growth by running a synthetic, very busy person through the reducer: about **1.7 M characters a year** when everything is used every day (about 0.44 M the log of what was done, 0.31 M workout records, 0.28 M meals, 0.26 M journal, 0.24 M water, 0.1 M hobby sessions, 0.06 M check-ins), so the hard limit is about two years away for that person and years away for most. At 2.2 M the Settings page suggests a download; at 3.0 M CleanFlow asks, offers a full download first, and only then makes room, in order: **thin** (old water kept as one total per day, old workouts lose their exercise-by-exercise list; totals unchanged), then, only if that is not enough, **trim** the oldest days of every history at once (log, meals, workout records, water, hobby sessions, check-ins, shopping lists) so every record starts on the same date. **What the person wrote is never removed**: the journal, their dishes, workouts, interests, books and links, and every setting. A note in the data (`retention`) says what was thinned or removed and where the history now starts. The validator keeps the newest items of every list and says so whenever it has to drop any.
- **Actions are idempotent and individually undoable.** Every logged action has an `entryId`; completing the same thing twice never double-counts, and Undo removes exactly its own entry (and restores that task's state only if nothing newer touched it).
- A running timer carries its task, so a "Just 5 minutes" habit finished after a reload is still logged as that habit.

## Analytics foundation (data only, no analytics UI yet)
Every logged entry records the template, level, difficulty, intensity, planned time of day, goals, plan version, day energy, local hour, timezone offset and, for moves and snoozes, where the task was due and where it went. Day energy is kept per day (`energyLog`), plan inputs get a stable `planVersion` (and a snapshot of the goals that plan could not serve, with the reason), and suggestions emit `recEvents` (shown / accepted / dismissed, with a reason code and the numbers behind it), each recorded once however many times a screen renders. Nothing leaves the device.

### What a day's record says (contract 2)
Three different facts are kept apart, because mixing them is how "ignored" gets invented:
- **Selected**: what the planner put on the day (`exposures[].items`, with `selectedAt` and the energy it was selected under). Not the same as shown.
- **Left out**: due tasks the planner considered and did not select (`exposures[].left`), each with the planner's own reason (`not-enough-time`, `low-energy-day`, `not-a-cleaning-day`), the time, energy and budget at that moment. A left-out task is not an exposure and is never counted as skipped or failed.
- **Seen**: set by the Today screen, only while the page is visible, when the task is actually rendered (`seenAt`; for left-out tasks, when the "left out of today" list is opened). Rendered, not scrolled to or read. Opening Settings first records the day's selection and marks nothing seen.

A day record is written when the app is opened while visible, even if nothing is planned, so a day with no record between two records means the app was not opened. Before records began, in removed history, or under the older record format, a day is **unknown**, never "not opened". Records written before contract 2 keep their unknowns (no invented seen, no invented reasons), and a same-day old-format record is left exactly as it was. Re-renders, StrictMode, reloads and a second tab add nothing: first-seen times are never overwritten and a repeat adds no write.

Each entry also says which screen it came from (`surface`), whether the task was selected, left out, or not planned that day (`planned`; absent = unknown), the date the occurrence was due (`fromDue`; `null` for Just 5 minutes and rough-day steps), and which part of a split task it was (`part`).

## Behaviour insights
There is no Behaviour Analysis screen yet. The suggestions that exist read only what the person **did** (entries), and, where Today recorded it, what was shown. They share these rules (`src/domain/behaviour.ts`, `learning.ts`, `progression.ts`):
- "No completion" is never a skip. A skip is an explicit skip; a snooze, a move and a timer stopped early are each their own thing.
- Days the person declared low energy are not read as "this is too big". Just 5 minutes, the rough-day steps and the reset sequence are not the routines and are left out of routine evidence.
- A window that reaches into history removed to save space is not read at all (a short count there would look like a quiet stretch). Where the evidence is unreliable, the suggestion is withheld, not softened.
- Nothing says why anyone did or did not do something. Every suggestion is optional and shows its numbers. Only the step up adds work; it needs a yes, and it is held back on low-energy stretches, by missing history, and when most of what was shown went undone (judged only once ten days of that are known).

## ## Your patterns
A read-only page (Progress → "Your patterns", or More) that summarises what the app recorded over the last 7, 14 or 28 days. It uses `summarizeWindow` and `dayStatus` from `src/domain/behaviour.ts` and adds no model of its own (`src/domain/patterns.ts`).
- **Days**: opened, not opened, used but not tracked, unknown, each with a text equivalent. A gap is "not opened" only when records exist on both sides of it.
- **Tasks shown on Today**: completed, skipped, snoozed, moved, timer stopped early, and **shown with no recorded action** (the absence of an entry: never a skip, and the page says it does not know why). Today is not over, so what was shown today with nothing logged yet is "still open", not "no action".
- **Selected, but not shown**, and **left out by the planner** grouped by the planner's recorded reason. A left-out task is never counted as shown.
- **Notes**: days whose history was removed to save space (never treated as quiet), and days recorded before display tracking (unknown, left out of the counts, never filled in).
- **Not enough recorded yet**: below 3 opened days or 5 shown tasks in the window, the page shows the day coverage and that notice instead of counts. The thresholds are app choices (`PATTERN_RULES`), not statistics.
"Shown" means Today displayed the task while the page was visible. It does not mean it was read.

## AI coach (optional)
Off until you choose it. "Ask AI for suggestions" first shows exactly what would be sent (a list of counts and the exact JSON), who receives it, and what is not sent; nothing leaves the browser until you press Send, and Cancel sends nothing.
- **What is sent**: the window length and 24 named counts (`src/domain/coach/metrics.ts`). No name, task or room text, dates, ids or notes: there is nowhere for free text to go, and the server rejects any request that is not exactly that shape or whose counts cannot add up. It is only offered when the window has enough recorded data.
- **What it may do**: explain the counts in plain language and offer up to three optional ideas that point at things that change nothing in the plan ("Just 5 minutes", "I only have…", the "left out of today" list, the Tomorrow tab, this page). **What it may not**: diagnose, guess at causes or feelings, claim something was seen, skipped or ignored unless that count is recorded, rest an idea on unknown days or removed history, or change anything. It has no access to your data or plan; it can only produce text.
- **Checked in code, not trusted**: every answer is validated against the exact request (`validateCoachOutput`): each cited count must be in the request, every number in the text must be a cited count, banned wording (causes, emotions, health, pressure, plan changes, "ignored") and unsupported words (skipped, snoozed, shown… without that count above zero) are dropped, and the strength label is capped by how much data there is. If nothing survives you see "I couldn't create a reliable suggestion from this data." The browser checks the server's answer again against the request you reviewed. Each answer shows its evidence window and counts, is labelled AI-generated, and can be dismissed or asked for again.

### Provider and deployment
**Local mode must be selected deliberately.** The app chooses between "local" (no accounts) and "accounts" from the server's own valid answer to `GET /api/config`. A 404 or 405 from a proxy, an HTML page, malformed JSON or an error status is *not* taken to mean "no server": the app shows a "try again" screen and leaves stored data alone. A deployment that really has no server (GitHub Pages and similar, or the phone app) must say so when it is built: `VITE_CLEANFLOW_STANDALONE=1 npm run build` (`npm run cap:sync` already does). Without that setting such a deployment shows the "try again" screen instead of the app.

The AI needs a server: the key must never be in the browser, so a static host alone (GitHub Pages and similar) shows the coach as unavailable and sends nothing. Three ways to run the endpoint, all the same code (`server/coach/handler.ts`, a plain `(Request) => Response`):
1. **Local development**: `npm run dev:coach` on a Mac (key from the Keychain, see "Try it on your Mac"), or `npm run dev` / `npm run preview` with `ANTHROPIC_API_KEY` set in your shell by a means that does not record it (not typed on a command line, not a `VITE_` variable, not committed).
2. **One Node process** serving the built app and the endpoint: `npm run build && npm run build:server && ANTHROPIC_API_KEY=… npm start` (`PORT`, `HOST`, default `127.0.0.1`; use `0.0.0.0` in a container).
3. **A serverless or edge platform**: mount `createCoachHandler()` from `server/coach/handler.ts` behind `/api/coach` and `/api/coach/status`. That glue is not written or tested here.

The only adapter so far is Anthropic's, through the official SDK (`server/coach/anthropic.ts`); `server/coach/provider.ts` is the small interface to implement for another. Settings are server environment variables only: `ANTHROPIC_API_KEY` (required), `COACH_MODEL` (default `claude-haiku-5-5`; set it to, for example, `claude-sonnet-5-5` or `claude-opus-5-5` for more capable and more expensive answers), `COACH_PROVIDER`, `COACH_API_BASE_URL`, `COACH_DISABLED=1`, `COACH_TIMEOUT_MS`, `COACH_MAX_OUTPUT_TOKENS`, `COACH_COOLDOWN_SECONDS`, `COACH_DAILY_PER_CLIENT`, `COACH_DAILY_TOTAL`, `COACH_ALLOWED_ORIGINS`, `COACH_TRUST_PROXY` (documented in `server/coach/config.ts`). A start-up line says whether the coach is on, naming settings but never values.

### Try it on your Mac
1. **See it off first (free).** `npm install && npm run dev`, open http://localhost:5173, go to Progress → Your patterns and press "Ask AI for suggestions" on a window with enough data: it says the coach is not set up and sends nothing.
2. **Get made-up history to try it on.** `npm run sample-data` writes `cleanflow-sample-data.json` (git-ignored, 21 days of fake history). In the app: Settings → Restore from a file → Replace my data. This replaces what the app holds (it backs up first), so use a separate browser profile if you have real data.
3. **Create an Anthropic account, add a small amount of credit, set a spend limit and create a key** at https://platform.claude.com (Settings → Billing, Settings → API keys). API billing is prepaid credits, separate from any Claude subscription; credits expire after a year and purchases are non-refundable. Leave auto-reload off while testing.
4. **Store the key in the macOS Keychain, not in a file, Git, the browser or shell history.** Run `security add-generic-password -a "$USER" -s cleanflow-anthropic-api-key -w`; it prompts for the key with no echo. (Or add it by hand in Keychain Access → File → New Password Item, using that name.)
5. **Start the app with the key.** `npm run dev:coach` reads the key from the Keychain for that one process (`scripts/with-keychain-key.sh`) and prints `[ai] AI suggestions: on (anthropic, model claude-haiku-5-5)` without the key. macOS may ask once to allow access to the Keychain item.
6. **Ask, review, send.** Progress → Your patterns → Ask AI for suggestions → read what would be sent → Send these counts. Each answer shows its evidence, and nothing in your plan changes. Terminal lines such as `{"event":"coach.provider-error","code":"auth"}` name a problem (`auth`: key rejected; `bad-request`: model name, credits or spend limit; `rate-limit`; `timeout`) and never contain your data or the key.

Do not put the key in a `.env` file expecting it to work (the server reads only the process environment), do not prefix it with `VITE_` (that ships it to the browser), and do not type it into a command line (that records it in shell history).


### Cost and privacy
- **Cost**: each request calls a paid provider API, billed to whoever owns the key. This is separate from any Claude or coding-assistant subscription or credits, and the Console bills it from prepaid credits. The default model, `claude-haiku-5-5`, is the cheapest tier: Anthropic's pricing page lists $0.10 per million input tokens and $0.50 per million output tokens (for prompts up to 100,000 tokens). A request here is about 4,500 characters in (my estimate is roughly 1,500 tokens; I have not been able to measure it) and at most `COACH_MAX_OUTPUT_TOKENS` (default 4,000, including the model's own thinking) out, so a typical request should cost a fraction of a cent and the worst case about two tenths of a cent at list prices. Check the Console's Usage page for the real figures, and re-check the pricing page: prices change. Controls: one small request per click, a token cap, a cooldown between requests (default 30 s), per-client (20) and whole-process (300) daily limits, retries off. The limits live in memory per process, so on several instances each enforces its own; set a spend limit in the Console as the real backstop.
- **Privacy**: the request and the answer are never logged or stored by the server (log lines carry an event name and a short code only), and provider error text is never passed on. The answer is not saved in your data. The provider receives the counts you reviewed, under its own data policy.
- **Not live until configured**: the server code is tested against a stand-in for the provider's HTTP API; a real call needs your key and has to be tried separately.

## The assistant (optional, same server and key as the coach)
One assistant helps with three jobs: **suggest meals** for some days, **plan my movement**, and **ideas to try** (Meals → Plan, Movement → Plan, Learning → Discover). The coach above explains counts; this one *chooses among options the app already filtered*. The two share the server's settings, key and provider adapter (`createApiHandler` in `server/api.ts`) and nothing else: the coach's contract is untouched.
- **The app filters first, on the device.** Your diet, allergen and dislike settings, equipment, what you would rather not do, rest days, today's energy and "not for me" choices are applied *before* anything is built (`src/domain/assist/build.ts`), so the assistant never sees a recipe or workout you filtered out. Those settings are not sent, and the diet and budget tags that would repeat them are stripped. The screen still says the list can hint at them.
- **What is sent** (`AssistRequest`): the days and meal slots, a count, a note you typed for this request, and up to 40 candidates, each only `id`, `name`, `minutes`, `tags` and `slots`. Your own dishes and workouts are left out unless you switch them on, and only their names go. The server rejects anything not exactly that shape. Journals, check-ins, water, health data, interests, books and notes have no place in it (tests check this, including that planted text never appears in a request).
- **Review before sending, and again before adding.** "Ask the AI" shows exactly what would be sent, who receives it and who is billed; nothing is sent until "Send to the AI". The answer is a list of proposed items, each ticked by default, that you can untick one by one; nothing is added until you press the button, and Undo removes exactly what was added.
- **Checked in code, not trusted** (`src/domain/assist/contract.ts`, `text.ts`; the same checks run on the server and again in the browser): every item must name a candidate that was in the request, on a day and slot that was in the request, at most one thing per slot or day; the minutes and intensity come from the app's own catalogue, never from the assistant. Reasons are limited to 140 characters, may only use numbers from the request, and are dropped if they contain nutrition, health, body or weight, medical, safety (allergy), price, pressure, markup or "I have added it" wording. An answer that cannot be checked is shown as nothing, calmly. Text you type is marked in the prompt as untrusted, and an instruction in it cannot add a candidate because anything outside the request is dropped.
- **No AI needed.** "Suggest with the app" makes the same kind of proposal with plain rules (rotate through what fits, spread sessions out), works offline, and goes through the identical review; it is labelled "Suggested by the app, no AI". When the AI is not set up the owl shows asleep and says so.
- **Not live until configured.** The endpoint is tested against a stand-in for the provider (`tests/assistServer.test.ts`); the browser suite answers `/api/assist` itself. A real call needs your key and has to be tried separately. Cost and privacy are as for the coach: usage is billed to the key's owner, and the server logs event names and short codes only, never a request or an answer.

## Reminders, calendar, alarms, notes and health
Settings has *Reminders* and *Health data*. They are described, with what was checked in the platforms' own documentation and what could not be, in **[docs/native-integrations.md](docs/native-integrations.md)**. In short:
- A **reminder** is derived from the plan every time, one per planned occurrence with a time (`src/domain/reminders/`), so doing, moving, archiving or deleting an activity cancels it by the same comparison; there is a default lead time, an override or "off" per activity, quiet hours (skipped, not delayed), snooze for one occurrence, and a plain list of what is coming and why something will not be sent. **In a browser a reminder appears only while CleanFlow is open, and the screen says so**; the phone app (Capacitor, `capacitor.config.ts`) can hand them to the operating system so they arrive when the app is closed. "On" never means "working": the line under the switch comes from what the device actually allows.
- A **calendar file (.ics)** makes calendar events with the calendar's own alert. Events, notifications, Apple Reminders and alarms are four different things; CleanFlow makes the first two, and says it sets no alarms and adds nothing to Apple Reminders.
- **Health data** (Apple Health, Health Connect) is optional, read-only, off by default, and not available in a browser (the screen says so instead of showing a switch). "Connected" needs a device with the service, an allowed kind of data and a read that worked. It is stored apart from your own records, shown labelled, and never completes a plan item, uses your minutes, edits your water log or reaches the AI.
- **Verification status**: all of this is source-implemented and unit-tested; the browser behaviour is browser-tested; **nothing native has been built or run** (no Xcode, and the Android SDK cannot be reached from this environment), so native notifications and Health reads are untested on a device. The doc lists what remains.

## Accounts, the free trial and subscriptions (optional server mode)

The app asks its server which mode it is in (`GET /api/config`). With no accounts it is the single-device app described everywhere else in this file, and **nothing below applies**. With `CLEANFLOW_MODE=accounts` (PostgreSQL, Better Auth, a Stripe account; see [docs/deployment.md](docs/deployment.md)) it adds:

- **Accounts**: sign-up with email confirmation, sign-in and out, password reset and change, account deletion; each account's plan is stored under its own key on the device, so two people sharing a browser never see each other's data.
- **A 14-day free trial**, started only by ticking a box and pressing a button, with dates from the server's clock (it cannot be restarted from the browser) and one per person.
- **A subscription**: €25 a month or €255 a year (exactly 15% off), paid on Stripe's own pages; the server, not the browser, says whether a payment happened. Cancel at the end of the period (access continues to its exact end), resume, failed-payment grace, and recovery screens for each payment state. A monthly AI allowance, the same for both plans, comes with it (`docs/billing.md`).
- **The planner gate**: the planner opens only while the server says the account has full access. Otherwise the person sees Trial & plans in a "paused" form, and account management, billing, export, deletion and Data & backup stay open. See "What the gate is" in [docs/billing.md](docs/billing.md).
- **Data & backup**: copy data saved before accounts into the account (preview, restore points, never silently replacing anything), and an optional, manual cloud backup in which the journal and imported health readings are off by default (`docs/data-and-backup.md`).

**What the gate is and is not.** It is an interface rule: the planner's code and data live in the browser, so someone who edits the page can still open the screens. What the server enforces whatever the browser does: the AI endpoints, cloud backup uploads, checkout, billing and deletion. This is stated in the app's own docs rather than hidden.

**Verified here, and how.** Real PostgreSQL 16 and real Better Auth in `npm run test:db`; a real Chromium against the real API in `npm run e2e:accounts`, `e2e:plans`, `e2e:subscription`, `e2e:backup`, `e2e:gate` and `e2e:a11y`; the local single-device app in `npm run e2e` and `npm run e2e:standalone`. The payment provider in those tests is a **local stand-in** that the real Stripe SDK talks to (`tests/support/fakeStripe.ts`): it proves this app's behaviour given plausible provider answers, **not** Stripe's. Nothing was run against Stripe, a real email provider, a phone, or a screen reader (`e2e:a11y` uses axe-core, a keyboard walk and emulated preferences, which is not the same thing). What remains before anyone is charged is listed in [docs/implementation-checklist.md](docs/implementation-checklist.md) under "External blockers".

## Testing
`npm test` covers the pure domain, the reducer and the storage layer (and, when PostgreSQL is not available, skips the account tests that `npm run test:db` runs for real). `npm run e2e` drives a real browser: `flow.mjs` (the main journey), `responsive.mjs` (every screen, sheet, onboarding step and the newer states at 320, 360, 390, 430, 768, 1024 and 1366 px, with overflow and accessibility checks), `integrity.mjs` (recovery, confirmation, duplicates, closing mid-save, timers, time-aware Today and home routines, life-only users, goal coverage, budgets on Today / Tomorrow / the week, low energy, a three-year history), `sync.mjs` (two tabs on the same data: no write loop, both tabs' work survives, a stale tab backs up the latest state, no room for a backup), `behaviour.mjs` (what a day records: selected vs left out vs seen, Settings-first opens, a background tab, two tabs, the fresh-start wording) and `coach.mjs` (Your patterns and the AI flow against a stand-in provider on its own dev servers: counts against an independent oracle, nothing sent before Send, Cancel, grounded and ungrounded answers, timeouts, the key absent from every response, storage and the built bundle, layout at every width)), `sections.mjs` (choosing sections, the one shared plan, caps and conflicts, the one-time introduction), `meals.mjs` (recipes, the week, dishes, shopping lists and their arithmetic, sharing), `movement.mjs` (workouts, a guided session start to finish, water, check-ins, breathing, journal), `learning.mjs` (discover, first tries, logging and undo, the reading list, appearance with no font requests and a readable accent, the owl, layouts at the largest text) and `assist.mjs` (the assistant against a stand-in for `/api/assist`, what is and is not sent, reminders, the calendar file, health data in a browser, layouts at the largest text). Unit suites worth naming: `assist*.test.ts` (the request and proposal contracts, candidate safety, the server, the controller), `reminders.test.ts`, `health.test.ts`, `retentionAll.test.ts` (measured growth and compaction over every history) and `backupAll.test.ts` (everything new survives a backup, restore and two tabs). `npm run storage-growth` prints where saved characters go.
